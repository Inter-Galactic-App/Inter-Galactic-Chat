# Apple native payload enumeration and hidden-limb sweep

**Measured 2026-08-19 (MAC/REVIEW).**
**Artefact: `InterGalactic.ipa`, CFBundleShortVersionString 0.8.0, CFBundleVersion 993.**

## Read this first: which artefact this is, and which it is not

This is **not** the 0.8.1+1003 release candidate. No Apple release candidate has
been produced yet. The archive measured here is the retained
`build/ios/archive/Runner.xcarchive` and its `build/ios/ipa/InterGalactic.ipa`
export, created 2026-07-09, `method = app-store-connect`, single `arm64` slice,
signed with an Apple **Development** identity.

The standing project rule is that licence pins are measured against retained
release payloads. **This one is not a release payload, so nothing here is
offered as a release pin.** What it is good for is the thing that was actually
missing: nobody had ever opened an Apple binary. Composition — which components
are inside, and which of them nothing had noticed — is what this measures, and
that is stable across a patch bump for a reason that was itself checked rather
than assumed:

> `intergalactic/ios/Podfile.lock` has not changed since commit `cb0753e1`
> (2026-07-07), which is **before** this archive was built. Its SHA-256 is
> `e348d4e286953e323d1159c2a12d4cc7dcddb5e8639b7183ae900cb9743e0eee` both at
> that commit and on `main` today — 0 commits have touched it since. The 71
> pods in this artefact are the 71 pods 0.8.1+1003 will build.

The digests below therefore pin *these bytes*, and are the shape the release
candidate's own row must take. **Re-measure against the real archive before any
digest here is treated as a release fact.**

## Method

`Payload/` was walked in full — 277 files — and every file whose first four
bytes are a Mach-O or fat magic was recorded. Twenty-five qualified. All three
fat binaries carry exactly one `arm64` slice (`lipo -detailed_info`), so a
per-path digest is unambiguous and no per-slice split is needed.

## The hidden-limb sweep

The point of this pass is the one the Android work proved is worth doing: a
generated notice surface enumerates *packages*, so a component statically linked
into somebody else's binary is invisible to all of them. On Android that is
exactly how KISS FFT shipped under BSD-3-Clause with its notice in none of the
three surfaces that reach a user.

For each of the 25 binaries, `nm -arch arm64` and `strings -a -n 4` were dumped
and 51 symbol families were probed, separating **defined** symbols (the code is
in this binary) from **undefined** (it is imported from another).

### The first run was vacuous, and the controls are why that is known

The first pass reported zero hits for every probe including FreeType inside
`Freetype.framework`. Mach-O symbols carry a leading underscore, so
`\bFT_Init_FreeType\b` never matched `_FT_Init_FreeType` — `_` is a word
character, so there is no word boundary before `FT_`. The probe list was intact;
the parser was wrong, and a sweep that finds nothing looks identical either way.

After normalising the leading underscore, the controls behave in both
directions:

- **positive** — FreeType, HarfBuzz, libpng, FriBidi, dav1d, Mbed TLS, libass,
  libxml2, uchardet, mpv and avcodec each resolve as *defined* in their own
  framework and *undefined* in the frameworks that call them, which is what
  dynamic linkage between 18 separate frameworks should look like;
- **negative** — `zzqqxx_nonexistent_probe` returns 0, as do 30 real probes for
  components this bundle genuinely does not carry: expat, brotli, opus, speex,
  libjpeg, libwebp, BoringSSL, libyuv, libvpx, libsrtp, usrsctp, protobuf, lua,
  zstd, lz4, libsodium, c-ares, pcre, curl, vorbis/ogg, FLAC, libarchive, crc32c,
  double-conversion, libplacebo, libbluray, aribb24, jsoncpp, openh264, aom,
  x264, x265, fontconfig.

`zlib` and `iconv` appear as **undefined only**, in six and three frameworks
respectively. That is the iOS system `libz` / `libiconv` being resolved, not a
bundled copy — the same finding that makes zlib an Android-only notice.

### Probing by prefix as well as by name

A probe list is bounded by what the person writing it thought of, so the defined
C symbols of the three largest binaries were also bucketed by prefix, with no
target in mind. `Runner` has 9,298 defined symbols; after excluding C++, Swift,
Objective-C, and the Rust and SQLite families, **252 remain and every one of
them is SDWebImage, a Flutter plugin constant, or `flutter_rust_bridge`.**

`libswift_Concurrency.dylib`, `objective_c.framework` and the Broadcast
Extension were checked the same way: 3,283, 373 and 28 defined symbols
respectively, all accounted for.

## What the sweep found

### 1. SQLite 3.52.0, statically merged into `Runner` — already recorded

274 defined `sqlite3_*` symbols, version string `3.52.0`, source id
`2026-03-06 16:01:44 557aeb43869d…`. This is the `sqlite3` pod, already carried
as `ios_pods` → `sqlite3` 3.52.0, Public-Domain. No obligation, no gap. Noted
because a reader will find it and should not have to re-derive that it is fine.

### 2. Abseil, inside `WebRTC.framework` — inside an existing record

Present only as a type in WebRTC's own exported C++ signatures
(`N4absl12AnyInvocable…`); its own symbols are internal. Abseil is Apache-2.0
and inside the `WebRTC-SDK` record's scope. Recorded, not reopened here.

### 3. The Rust encryption tree, statically merged into `Runner` — A REAL GAP

**59 Rust crates plus the Rust standard library are linked into the `Runner`
executable and were named in nothing.**

`flutter_vodozemac` ships no prebuilt library. Its podspec runs cargokit at
pod-build time and force-loads the result:

    OTHER_LDFLAGS = -force_load ${BUILT_PRODUCTS_DIR}/libvodozemac_bindings_dart.a

so the whole tree lands inside the app executable with no file of its own. On
Android and Windows the same tree arrives as `libvodozemac_bindings_dart.so` /
`.dll` — **this is not an Apple-only gap**, and the Android row's finding that
"record and artefact agree" for that `.so` was about vodozemac itself, not about
what vodozemac pulls in.

Measured against `docs/release/THIRD_PARTY_LICENSES.json` before the fix, with
`freetype` ×18 as the control proving the search worked:

| probe | hits in the inventory |
| --- | ---: |
| `vodozemac` | 8 |
| `curve25519`, `ed25519`, `tokio`, `serde`, `prost`, `anyhow`, `hashbrown`, `dashmap`, `aes`, `base64ct`, `memchr`, `rand_chacha` | **0 each** |
| `Cargo.lock` anywhere in either repo's docs | **0** |

The crates are MIT, Apache-2.0, BSD-3-Clause, Unlicense, 0BSD, Zlib and BSL-1.0.
Every one of those requires its notice to travel with a binary distribution.
Provenance, the roster, and the fix are in
`../license-sources/rust-crates/VODOZEMAC-RUST-TREE.md`.

### 4. `libswift_Concurrency.dylib` — recorded with an explicit boundary

Apple's Swift concurrency back-deployment runtime, copied in by Xcode. Swift is
Apache-2.0 with the Runtime Library Exception. It now has an inventory record.
Its in-app notice question is deliberately left open rather than answered here:
no authoritative copy of the Swift `LICENSE.txt` exists on this host, and this
project's repeated failure mode is capturing a licence text from a plausible but
wrong source. Routed to S&C as a named boundary, in the same shape as the
Windows Direct3D terms-route boundary.

## What this does not establish

- It is not a release pin. See the first section.
- A symbol sweep proves presence, never absence in general. It proves absence
  only of the families probed, which is why the probe list and its controls are
  written out above rather than summarised as "clean".
- `hashbrown` appears in the bindings lockfile at both 0.14.5 and 0.15.2. Only
  0.14.5 is evidenced by a cargo path in this binary, so only 0.14.5 is claimed.
- The NSE is not in this artefact. 0.8.0+993 carries one extension, the
  Broadcast Extension. If the notification service extension ships in 0.8.1, the
  release candidate will have a 26th Mach-O that has never been swept.
