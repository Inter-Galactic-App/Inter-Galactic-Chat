# Inter Galactic Release Checklist

## Purpose

This checklist is the release manager's runbook for desktop and mobile builds.
It covers release candidate preparation, build creation, signing, update
manifest validation, publication order, post-release verification, and rollback
readiness.

Maintainer note: this runbook is public app-repo guidance. It describes what a
release must prove, not one maintainer's private helper-script layout. Keep
personal workspace automation notes outside this repository.

Do not use this document as permission to change app behavior. Product fixes
must land through normal scoped changes before a release candidate is cut.

## Current Pipeline Findings

- Version identity lives in `intergalactic/pubspec.yaml` as
  `version: X.Y.Z+build`. Windows MSIX metadata currently mirrors this with
  `msix_version`.
- Local maintainer automation may wrap the portable release steps for Windows,
  Android, web, and update-manifest packaging. Private helper names and local
  artifact folders belong in workspace-private docs, not this public checklist.
- The release packaging flow signs the Windows app executable and installer when Windows
  signing is enabled and signing credentials are configured. A trusted
  Authenticode `Valid` installer is the preferred user-trust path; the
  open-source fallback is an unsigned or untrusted installer only when HTTPS,
  SHA-256 verification, `platforms.windows.allow_unsigned_auto_update: true`,
  and explicit updater approval are all present. Checksums are generated after
  the final signing/packaging decision, and `latest.json` is uploaded last so
  update prompts do not point at missing assets.
- `latest.json` is generated by the active release packaging flow; the
  app-local `intergalactic/scripts/generate_update_manifest.dart` remains a
  compatible helper but is not the active Windows release path.
- The in-app updater reads `UPDATE_MANIFEST_URL`, parses `version`,
  `build_date_ms`, `release_url`, `notes`, `notes_url`, and `platforms`, then
  compares the manifest version against the baked `BuildConfig.VERSION_TAG`.
- GitHub workflows currently provide manual build jobs, static analysis on PRs,
  manual integration tests, and a security-review workflow. They are not the
  signed production release pipeline.
- The security-review workflow runs the repo-owned
  `.github/scripts/security-review.py` gate on pull requests. It catches
  committed secret-bearing files, high-confidence token literals, and missing
  release security gate references. GitHub Dependency Review is available as an
  opt-in pull-request job when the repository supports it and
  `ENABLE_DEPENDENCY_REVIEW` is set to `true`.
- iOS can be built through `intergalactic/scripts/build_release.dart
  --platform ios`, but IPA export requires macOS/Xcode/signing assets. The
  project file has app-store style Runner signing configuration and a Broadcast
  Extension target whose version fields must be checked before TestFlight/App
  Store submission.
- Fastlane Android text metadata exists, but copied Commet screenshot/image
  assets were removed on 2026-06-13. Future store submission needs current
  Inter Galactic-owned/listing images. No current Play Store or App Store
  upload lane was found in this inspection.

## Release Candidate Gate

Complete these before building any public or semi-public release candidate.

- Confirm the intended release scope: Windows desktop, Android APK, iOS
  TestFlight/App Store, web, or a subset.
- Confirm the current branch and commit are the intended release source.
- Confirm no unrelated dirty files are being swept into the release.
- Confirm open release blockers in the maintainer issue tracker and any
  private release coordination notes for the target channel.
- Confirm `docs/CHANGE_LOG.md` and public release notes have the target version
  content.
- Confirm the maintainer `security-checklist.md`, `dependency-review.md`, and
  `runtime-privacy-review.md` release gates have been completed.
- Confirm the latest `security-review` GitHub workflow passed for the release
  branch or run the same local gate from the app repo with
  `python .github/scripts/security-review.py --repo-root .`.
- Confirm `intergalactic/pubspec.yaml` has the target `X.Y.Z+build`.
- Confirm feature flags and environment-backed values are intentional:
  `UPDATE_MANIFEST_URL`, `GIF_API_BASE_URL`, Spotify, Steam activity proxy,
  Android Google Services, and Windows detached call windows.
- Confirm media/ML-backed features have current S&C disposition before release:
  for Emoticon Creator, the accepted mobile shape is iOS Apple Vision plus
  Android ML Kit unbundled Subject Segmentation; any desktop ONNX model,
  cloud background-removal provider, bundled model artifact, or different
  mobile ML dependency requires a new S&C/release review before shipping.
- Confirm the Windows installer trust path for this release:
  - Trusted signed path: signing secrets are available on the release machine,
    are not staged in git, and the installer Authenticode status is `Valid`.
  - Open-source unsigned consent path: HTTPS URLs, SHA-256 metadata,
    `platforms.windows.auto_update: true`,
    `platforms.windows.allow_unsigned_auto_update: true`, and the updater
    approval dialog are all verified before installer execution.
  - Manual-download opt-out: `IG_WINDOWS_AUTO_UPDATE=0` is intentionally set
    for the release run and the reason is recorded in the release record.
- Confirm diagnostic export safety has been sampled for this release. As of
  2026-05-15, Developer Logs were user-verified clear of secrets; LiveKit/WebRTC
  call diagnostics still require a release-time spot-check before closing the
  S&C diagnostic gate.
- Confirm rollback artifact availability for the current live version before
  replacing `latest.json`. Local maintainer live publishes must create the
  rollback-proof archive before copying new mirror files; dry runs must not
  write archive files.

## Same-Version Build-Bump / Hotfix Gate

Release-cycle evidence is scoped to the semantic version (`X.Y.Z`). Exact
artifacts are scoped to the full build identity (`X.Y.Z+build`).

Use this gate when a release issue, hotfix, or final tester rebuild increments
only the build number while the semantic version stays the same.

- Keep one release record for the semantic version, such as
  `release-record-v0.8.0.md`.
- Add a build-ledger row for every candidate build number in that semantic
  version.
- Compare the previous accepted candidate source against the new candidate
  source before deciding what evidence can carry forward.
- Record which source-cycle and risk-smoke gates were triggered by the changed
  paths, and which gates can carry forward because their inputs did not change.
- Treat unclassified changed paths as a stop condition until the release owner
  classifies their release impact.
- Always rerun exact artifact evidence for the new build number: package
  identity, installer/APK/IPA output, source archive, checksums, signing or
  unsigned-consent trust path, `latest.json`, rollback-proof, and updater smoke.
- Do not carry forward `latest.json`, checksum, artifact-hygiene, signing, or
  auto-update proof across build numbers.
- If the semantic version changes, open or clone into the new semantic-version
  release record instead of continuing the old one.

## Pre-Release Validation

Run validation against the release candidate before publishing.

- Static analysis and focused tests for changed areas have passed or have a
  documented exception.
- When Android is in scope, Android Gradle/Kotlin deprecation and compile
  warnings from the latest release evidence are tracked before the next Android
  toolchain bump, including FlutterPlugin.kt / PluginHandler.kt warnings and
  Gradle 9 deprecation debt.
- Security review automation has passed:
  `.github/workflows/security-review.yml` on GitHub or
  `.github/scripts/security-review.py` locally.
- Dependency advisory automation has passed when GitHub Dependency Review is
  enabled for the repository, and Dependabot security/update PRs are reviewed
  or intentionally deferred for this release.
- Windows release build completes through the configured Windows release path.
- Android release APK completes through the configured Android release path when
  Android is in scope.
- iOS archive/export completes on macOS/Xcode when iOS is in scope.
- When Emoticon Creator is in scope, Android and iOS rebuilt-device photo
  smokes are recorded, Android first-use/offline ML Kit model behavior is
  accepted, and final store privacy/disclosure answers match the submitted
  artifact.
- Web build and sync complete through the configured web release path when web
  is in scope.
- Windows packaged app launches from the release output, not only from Flutter
  debug.
- Login, session restore, encrypted room access, notifications, media preview,
  calls, downloads, and update banner behavior are smoke-tested according to
  `test-matrix.md`.
- Release dry run completes far enough to produce/package local
  artifacts, sign them when that release path is configured, and generate
  `dist/updates/latest.json`.
- Generated `latest.json` is validated against the artifact checklist before
  any upload.

## Build And Package Sequence

Use the smallest release scope that matches the release intent.

1. Update version:
   - Bump build metadata for tester-facing rebuilds.
   - Bump semantic version when the release should present as a new patch,
     minor, or major version.
   - Rebuild the same version only for local validation or unpublished
     artifacts.

2. Build Windows:
   - Use the configured Windows release build path.
   - Keep the default patched libwebrtc path unless intentionally producing a
     stock-WebRTC fallback build.
   - Confirm the configured Windows artifact output is version-stamped with
     `X.Y.Z+build`.

3. Build Android when in scope:
   - Use the configured Android release build path for the default FCM APK.
   - Use the non-Google fallback path only when intentionally producing that
     artifact.
   - Confirm the configured Android artifact output is version-stamped with
     `X.Y.Z+build`.

4. Package release:
   - Run the release packaging dry run and select the intended target when the
     local tooling prompts for release scope.
   - For scripted dry runs, pass explicit scope arguments supported by the
     local release tooling.
   - Validate installer trust path, selected APK presence, checksums,
     changelog, source zip, and `dist\updates\latest.json`.
   - Run the live packaging/publish flow only after the dry-run artifacts are
     correct.
   - During live publish, confirm the rollback-proof archive step completes
     before any mirror asset copy begins.

5. Publish manifest last:
   - Upload `latest.json` only after installer/APK/checksum/source/changelog
     assets are already reachable.
   - If manifest upload fails, do not manually point users at the new version
     until manifest and assets agree.

## Post-Release Verification

Verify the live release from a clean client perspective.

- Download page shows the new version and links to the expected artifacts.
- `https://app.ourgalaxy.space/updates/latest.json` returns HTTP 200 and valid
  JSON.
- Manifest `version`, `version_name`, `build_number`, URLs, checksums, and
  notes match the shipped artifacts.
- Windows installer download succeeds and the downloaded file matches the
  selected trust path: Authenticode `Valid`, or the approved unsigned consent
  path with HTTPS, SHA-256 verification, manifest opt-in, and updater approval.
- SHA-256 checksum file contains the final Windows installer and any Android
  APK.
- A previous Windows build detects the update and opens the intended release
  URL or downloads the intended installer, depending on `auto_update`.
- A fresh install launches and can log in.
- An upgraded install preserves session restore and encrypted room access.
- Android APK installs/updates on a test device when Android is in scope.
- TestFlight/App Store build appears in App Store Connect when iOS is in scope.
- Release notes and known issues are visible in the intended public location.

## Release Decision Record

For each release, record:

- Release version and build number.
- Commit SHA.
- Platforms shipped.
- Build commands used.
- Signing status.
- Windows installer trust path: signed `Valid`, unsigned consent fallback, or
  manual-download opt-out.
- Artifact paths.
- Manifest URL and checksum file.
- Validation completed and skipped validation with reason.
- Rollback point: previous `latest.json` version and artifact URLs.
- Rollback-proof archive path and zip SHA-256 when a live publish runs.
- Known issues and upgrade risks copied from `release-notes-template.md`.

## Stop Conditions

Stop the release and do not publish `latest.json` when any of these occur:

- Target app does not launch from packaged artifact.
- Login or session restore fails.
- Encrypted rooms cannot decrypt after restart.
- Windows installer trust path is neither Authenticode `Valid` nor the approved
  unsigned consent fallback.
- Checksums do not match the exact final artifacts.
- Manifest points to missing, differently named, or unsigned/untrusted Windows
  artifacts without the required consent flag and updater approval path.
- Android FCM/embedded-ntfy mode is not the intended release mode.
- iOS signing/capabilities are inconsistent with the intended App Store build.
- A rollback artifact for the previous live release cannot be located.
